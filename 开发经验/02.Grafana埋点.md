# 针对taskinference进行部署调试

##### 查看容器配置，取消一号进程

```
kubectl get deployment -n dsp dspm-taskinference -o yaml
```

  关键配置位置：
  
```
  spec:
    template:
      spec:
        containers:
        - command:                    # ← 这是覆盖镜像的启动命令
          - /bin/sh
          - -c
          - tail -f /dev/null         # ← 当前的 1 号进程（保持这个命令即可）

这是一个保持容器运行的技巧：

- `tail -f`：持续读取文件末尾（follow）

- `/dev/null`：Linux 的空设备，永远没有新内容

- 结果：命令永远阻塞，保持容器运行，但**不做任何实际工作**
```

### 在宿主机器上

```
kubectl get svc -n dsp |grep apo
```

输出：
```
dsp-apollo-api   ClusterIP   172.18.31.8    <none>   8080/TCP    30m
```

```
curl http://172.18.31.8:8080/metrics | grep apollo_api_latency_seconds
```

构造请求（直接宿主机器执行）：

```
for i in {1..24}; do
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] 请求 #$i:"
    curl -s -w "  状态码: %{http_code} | 响应时间: %{time_total}s\n" http://10.65.245.95:8080/healthy
    sleep 1
done
```

解释：
```
• 原理链路（结合你的配置）：

  - 应用：apolloserver 中间件把接口时延等指标写入 /metrics，监听在 Pod 的 8080 端口（端口名 metrics）。
  - 抓取：Helm 新增的 VMPodScrape（apolloserver/scripts/chart/templates/vm-scrape.yaml，vmScrape: true）按 Pod 标签 app=dsp-apollo-api 抓取 PodIP:8080/metrics，数据写入
    VictoriaMetrics（或 Prometheus）。
  - 展示：Grafana 的数据源指向这个 VictoriaMetrics/Prometheus，面板查询 apollo_api_latency_seconds_*。只有在最近有接口请求时，rate(...[5m])/histogram_quantile 才有曲线。

  为什么节点 IP:8080 不通

  - Pod 未开 hostNetwork，Service 是 ClusterIP。节点 IP 上没有 8080 监听，所以连接拒绝。你能用 172.18.31.8:8080（ClusterIP）或 Pod 内 localhost:8080，是因为 kube-proxy
    转发 ClusterIP。

  如何确保数据能到 Grafana

  1. 抓取生效：
      - kubectl get vmpodscrape -n dsp 应看到 *-pod-monitor。
      - kubectl get endpoints -n dsp dsp-apollo-api，确保有 Pod IP，端口 8080。
      - 在 Pod 内 curl -s localhost:8080/metrics | head 确认暴露。
  2. 生成样本：
      - 调用几次 /apollo/internal/... 真实接口，让直方图/计数器有数据。
  3. 数据源正确：
      - Grafana 数据源 UID 要指向当前 VictoriaMetrics/Prometheus（你的 grafana.json 里是 PD1016327C161BF04）。
  4. 面板查询：
      - 关注查询里的时间范围和 rate 窗口（5m），确保有最近请求。
```
