# 1. 介绍

# 1.1.目的

简要介绍该设计要解决的问题（满足用户什么需求或者解决现有设计什么问题）。

为应对企业在数据安全建设中面临的非结构化数据管理挑战，本模块致力于解决客户在文件服务器、网盘、终端及本地存储等多种场景下非结构化数据持续流动所带来的识别与管理难题。当前客户普遍存在以下痛点：

 识别覆盖不足：传统识别手段对非结构化数据支持有限，识别率低、漏检频发，导致高风险数据难以被有效发现。

 格式复杂、运营成本高：不同部门和业务系统中的非结构化数据格式多样，依赖人工规则配置的识别工具使用门槛高，客户自运营负担重。

 结果可解释性弱：现有识别结果缺乏清晰的分类分级依据，客户难以理解判定逻辑，影响系统可信度与落地执行效果。

基于上述问题，本模块旨在构建一套统一、自动化、精准的非结构化数据识别与分类分级体系，具备以下核心价值：

 全流程自动化识别：实现对多来源、多格式非结构化数据的精准识别与分类分级，自动生成判定依据，大幅减少人工干预，提升识别覆盖率与准确性。

 语义化识别能力：融合大模型语义分析与多行业识别模板，突破传统关键词匹配的局限，有效识别隐含语义内容及非文本类文件。

 多场景一致支持：适配HTTP、FTP等多种协议及终端、本地目录、NAS、云存储等多样化数据来源，确保各类环境下识别效果的统一与可靠。

d. 携带资产关联信息，向模型平台提交分类分级推理任务

a. 模型平台的数据识别分发服务接收推理任务

b. 基于资产信息与分类数据配置，执行以下预处理：

i. 关键词匹配分析

c. 将topK分类结果与清洗后的数据组合构建prompt

d. 提交大模型进行深度研判，获取最终分类结果与推理依据

e. 数据识别任务分发模块对模型输出进行后处理

f. 将结构化结果返回至应用平台

2. 转换：对于被选中的文件，系统需要将其从无法被机器理解的二进制格式，转换为可供模型分析的标准化文本。这就是文件解析引擎的工作。它本质上是一个“翻译官”，其内部是一个精密的处理流水线：

a. 格式识别：通过文件头（魔数）等特征，准确判断文件真实格式（如DOCX、PDF、PPT），不依赖易篡改的后缀名。

b. 元数据提取：读取文件的“身份证”信息，如大小、创建时间等。

c. 内容提取：调用针对特定格式的解析器（如Apache POI for Office, PDFBox forPDF），剥去所有格式修饰，抽取出最核心的纯文本内容。

这个过程是为后续的模型推理准备干净、结构化的文本，才能被大模型有效理解并做出准确判断，文件解析模块祥见4.5.2章节。

3. 分发：最后，系统将解析后的纯文本内容，与文件的“身份”信息一同打包，组装成一个标准的推理任务。这个任务包包含了模型进行分析所需的全部上下文，然后被提交至模型平台。这标志着调度与解析阶段的结束，文件正式进入智能分析与研判阶段。

最终选择方案：方案2：文件元数据入库后触发采样策略后，执行文件解析

选择理由：

1. 文件采样选中后才进行解析，节省文件解析开销，系统整体性能较好；

2. 文件解析与分类分级任务异步进行，较大程度上提升整体链路性能，文件解析模块支持横向扩展。

存在问题：

1. 文件解析后留存Pulsar，对Pulsar的稳定性有一定的影响；

2. 针对不属于用户开启的采样文件，更改采样策略时，无法直接获取到文件解析后的内。

解决方案：

1. Pulsar中不传输解析后的纯文本，只传输fileId，在进行分类分级任务时，解析后的文本通过接口获取；

2. 内部运营提供业务回溯接口，支持对更改采样策略后，针对老文件的文件解析与分类分级进行回放的功能。

# 4.2.1.4. 方案对业务的约束

1. 非结构化文件的解析与文件内容分类分级对性能的影响比较大，采样策略中的配置不能配置全部文件；

2. 针对模型平台的配置需要增加GPU卡，以目前的1万文件分类分级的目标。

# 主要步骤：

1. 消息接收：任务调度模块从Pulsar消费文件分类任务消息

2. 采样决策：调用采样策略引擎，基于采样规则（固定比例、时间窗口、风险优先级、去重）判断是否需要对该文件进行分类分级

3. 文件解析：采样通过后，HTTP同步调用文件解析服务，解析文件内容并提取文本

4. 元数据存储：文件解析服务将文件元数据存入MongoDB，解析后的文本内容存入MinIO

5. 推理任务下发：任务调度模块将推理任务（包含fileId、textPath等）通过Pulsar下发到推理Topic

6. 模型推理：模型推理服务消费推理任务，从MinIO读取解析文本，调用LLM模型进行分类分级

7. 结果返回：推理结果通过Pulsar返回给任务调度模块

8. 结果存储：任务调度模块调用分类分级结果入库模块，将分类分级结果写入MongoDB，并更新资产（API或FTP目录）的敏感标签

采样不通过：直接丢弃任务，不进行后续处理

文件解析失败：记录错误日志，标记任务状态为PARSE_FAILED，不下发推理任务

 模型推理超时：设置超时时间（默认30s），超时后标记任务失败，支持重试机制（最多3次）

存储失败：记录错误日志，触发告警，支持重试机制

# 流程说明:

风险研判接口调用流程是系统对外提供的同步HTTP接口，供风险研判系统实时调用，获取文件的分类分级结果。该接口内置在任务调度服务中，支持两种调用模式：

快速查询模式：如果文件已经解析过（MinIO中存在解析文本），直接调用模型推理并返回

完整处理模式：如果文件未解析，先调用文件解析服务，再调用模型推理

触发条件：

 风险研判系统通过HTTP POST方式调用分类分级接口，传入文件ID和文件类型主要步骤：

1. 接口接收：任务调度模块接收HTTP请求，提取fileId和fileType参数

# 流程说明：

模型推理执行流程是将解析后的文本内容进行分类分级的核心环节，采用多策略融合与LLM推理的混合架构。该流程由独立的模型推理服务执行，先通过传统NLP算法（TF-IDF、TextRank、LDA、Sentence Transformer）进行多维度特征提取和初步筛选，再将候选类别提交给LLM进行最终推理校准，实现"快速筛选 + 精准判断"的两阶段推理。

设计思路：

 阶段一（快速筛选）：使用传统NLP算法从数十个候选类别中快速筛选出Top-K（如Top-5）候选类别，时延<2s

 阶段二（精准判断）：仅将Top-K类别提交给LLM进行深度语义理解和最终判定，时延5-8s

 优势：相比直接使用LLM推理全部类别，该方案可将推理时延从15-20s降低至8-10s，并提高准确率

触发条件：

 任务调度模块在文件解析完成后，通过Pulsar下发推理任务到inference-task Topic

模型推理服务作为Pulsar消费者，实时消费推理任务

主要步骤：

# 阶段一：任务接收与文本读取

1. 消费推理任务：从Pulsar的inference-task Topic消费推理任务消息（包含fileId、textPath等）

2. 读取解析文本：从MinIO读取解析后的文本内容（路径：/parsed/{fileId}.txt）

# 阶段二：文本预处理与分词

1. 中文分词：使用自定义jieba分词器进行中文分词，确保分类树中的关键词不被错误切分

2. 停用词过滤：过滤停用词（的、了、在、是等）和无效字符

3. 数字串净化：快速去除文本中无意义的数字串（如UUID、随机数），净化文本内容

4. 输出：洁净的、由关键词组成的词汇列表

# 阶段三：多模型特征提取与信号生成（并行执行）

1. TF-IDF提取：适用于结构清晰的新闻、报告等，计算词频-逆文档频率，提取重要词汇

2. TextRank提取：基于窗口化识别和图结构算法，不依赖文本结构，适用于文件解析产生的碎片化文本，提取关键词及权重

3. LDA主题模型：识别文本背后的潜在主题，侧重于宏观语义归属

4. 语义嵌入：使用Sentence Transformer模型将关键词转换为高维向量（768维），将语义信息数值化

5. 输出：关键词权重字典、主题关键词列表、词向量矩阵

# 阶段四：信号融合与相似度计算

1. 语义匹配计算：计算预处理后每个词的向量与预定义分类体系中各类别所有要素的余弦相似度

2. 权重加成：对于相似度超过设定阈值（如0.6）的词，将其相似度分数乘以TextRank权重，作为该词的最终贡献分数

3. 类别积分：一个类别下所有匹配要素的分数之和，再乘以匹配成功的要素数量，作为该类别的最终得分

4. TopK筛选：按得分降序排列，选择得分最高的前K个类别（默认K=5）

5. 输出：每个类别的综合得分和详细匹配词条记录

1. 进程异常退出

a. 检测机制：Kubernetes Liveness Probe每10秒检查一次进程存活状态

b.恢复策略：进程退出后，Kubelet立即重启Pod，重启失败则尝试重新调度到其他节点

c. 数据保护：进程退出前通过signal handler捕获SIGTERM信号，完成数据持久化和任务状态保存

2. 进程D状态（不可中断睡眠）

a. 检测机制：健康检查接口超时3次（30秒）判定为D状态

b. 恢复策略：Kubernetes强制终止Pod（SIGKILL），重新创建新实例

c. 预防措施：文件解析模块在独立进程中执行，使用超时控制防止IO阻塞

3. 服务卡慢（响应超时）

a. 检测机制：健康检查接口响应时间>5秒连续3次，判定为卡慢

b.恢复策略：标记为Unhealthy，流量不再转发到该实例，等待自动恢复或重启

c. 限流保护：接口层限流防止过载导致卡慢

4. 内存泄漏

a. 检测机制：监控进程内存使用率，超过Pod限制的90%触发告警

b. 恢复策略：Kubernetes OOM Killer终止进程，自动重启

c. 预防措施：定期进行内存泄漏检测，及时修复泄漏问题

b.文件解析服务连接失败

d.文件解析超时

e. MinIO上传文本失败

h. MongoDB连接失败

i. MongoDB写入超时

j. HTTP接口整体处理超时

b.超时控制：所有IO操作设置超时，防止长时间阻塞

c. 重试机制：网络/IO操作失败自动重试，指数退避

e. 数据持久化：本地队列缓冲，故障恢复后补偿写入

f. 监控告警：关键指标监控，及时发现异常

3. 可靠性保障覆盖率：

a. 所有高优先级风险（AP=H）均有对应改进措施

b.所有改进措施均有明确的改进效果描述

c. 形成完整的故障检测-恢复-补偿机制

    cfg := jaegercfg.Configuration{
    ServiceName: serviceName,
    Sampler: &jaegercfg.SamplerConfig{
    Type: jaeger.SamplerTypeConst,
    Param: 1,
    },
    Reporter: &jaegercfg.ReporterConfig{
    LogSpans: true,
    LocalAgentHostPort: "jaeger-agent:6831",
    BufferFlushInterval: 1 * time.Second,

    jLogger := jaegerlog.StdLogger
    jMetricsFactory := metrics.NullFactory

    tracer, closer, err := cfg.NewTracer(
    jaegercfg.Logger(jLogger),
    jaegercfg.Metrics(jMetricsFactory),
    )

    if err != nil {
    return nil, nil, err
