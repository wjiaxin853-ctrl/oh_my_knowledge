  **一、严重问题** **(Must** **Fix)**

  

  **1.** **Catalog** **单测断言与实际接口返回不一致** **(datacatalog)**

  

  **文件**: catalog/tests/test_api_server.py:60,81,100,118

  

  测试用例断言 data["data"]["isConnected"]，但路由 datasource_router.py:50 中 test_connection 接口成功时返回的是 data=None：

  

  # 路由实际返回：

  return BaseResponse(code="Success", message="连接成功", data=None)

  

  # 测试断言（会 NoneType 报错）：

  assert data["data"]["isConnected"] == True   # data["data"] 是 None!

  

  同样，失败场景也返回 data=None，但测试断言 data["data"]["isConnected"] == False。

  

  **结论**: 这些测试要么会失败，要么从未真正执行过。需要修正断言或修改路由返回 TestConnectionData。

  

  ---

  **2.** **异步端点中使用同步** **HTTP** **请求阻塞事件循环** **(apolloserver)**

  

  **文件**: apollo_api/utils/catalog_client.py:59, apollo_api/routers/datasource.py

  

  Apollo 的路由函数是 async def（如 async def test_datasources_connect），但 catalog_client 内部使用的是同步的 requests.post()。在 FastAPI 的 async 端点中，同步阻塞调用会阻塞整个事件循环，导致其他请求也被阻塞。

  

  设计文档 4.1.1 中标注了 "HTTP Client: httpx/aiohttp"，但实际用了同步的 requests。

  

  **建议**: 使用 httpx.AsyncClient 替换 requests，或将路由函数改为 def（非 async）让 FastAPI 在线程池中执行。

  

  ---

  **3.** **性能退化：创建/更新数据源时双倍连接开销** **(apolloserver)**

  

  **文件**: apollo_api/routers/datasource.py:155-167, 464-487

  

  原来 create_datasource / update_datasource 中先调用 get_engine_by_type 拿到 engine，然后复用同一个 engine 获取数据库列表。现在改成了两次独立 HTTP 调用：

  

  res = catalog_client.test_connection(...)    # 第1次建连

  database_list = catalog_client.get_databases(...)  # 第2次建连

  

  每次调用 Catalog 都会创建并销毁一个引擎连接。原来一次连接完成的事，现在需要两次网络往返 + 两次数据库连接。

  

  **建议**: 在 Catalog 侧提供一个组合接口 test_and_list_databases，或者在 Apollo 侧直接调用 get_databases（如果成功返回列表说明连接本身就是通的，失败则说明连不上）。

  **5.** **app-config.yaml** **中的配置未真正加载** **(apolloserver)**

  

  **文件**: apollo_api/utils/conf.py:265-268, scripts/chart/templates/app-config.yaml

  

  Conf 类中 catalog_api_base_url 和 catalog_api_timeout 是硬编码的类属性：

  

  catalog_api_base_url = "http://catalog-api-server:8081"

  catalog_api_timeout = 60

  

  而 app-config.yaml 中也定义了同样的配置：

  

  catalog:

    api_base_url: "http://catalog-api-server:8081"

    timeout: 60

  

  但没有代码将 YAML 配置加载到 Conf 中。YAML 中的值永远不会被使用——两处配置如果出现不一致会造成混乱。

  

  **建议**: 要么删除 app-config.yaml 中的配置（如果不需要运行时可配），要么补充 Conf 的初始化逻辑读取 YAML 配置并覆盖默认值。

  **10.** **TestConnectionRequest** **和** **GetDatabasesRequest** **字段完全相同** **(datacatalog)**

  

  **文件**: catalog/api/schemas/request_schemas.py

  

  两个 Request 模型的字段一模一样（reqId, type, ip, port, option），可以用继承或单一模型减少重复：

  

  class DatasourceRequest(BaseModel):

      reqId: str = Field(...)

      type: DataSourceType = Field(...)

      ip: Optional[str] = Field(None)

      port: Optional[int] = Field(None, ge=1, le=65535)

      option: Dict[str, Any] = Field(default_factory=dict)

  

  class TestConnectionRequest(DatasourceRequest): pass

  class GetDatabasesRequest(DatasourceRequest): pass

  **四、小问题** **(Minor)**

  

  **12.** **_filter_system_databases** **每次调用创建列表** **(datacatalog)**

  

  **文件**: datasource_service.py:226-229

  

  system_dbs_lower = [db.lower() for db in system_dbs]  # 每次创建列表

  return [db for db in databases if db.lower() not in system_dbs_lower]  # O(n*m)

  

  对于 Oracle 有 50+ 个系统库，可以预计算为 set 提升查找效率：

  

  system_dbs_lower = {db.lower() for db in system_dbs}  # set, O(1) lookup

  

  **13.** **reqId** **使用截断的** **UUID** **(apolloserver)**

  

  **文件**: catalog_client.py:47

  

  req_id = str(uuid.uuid4())[:8]

  

  8 位十六进制 = 4 bytes = 约 42 亿种组合，对于请求追踪来说冲突概率不高但也非零。建议至少用 12 位或完整 UUID，方便排查问题时精确关联日志。
